# Call Me Maybe

## Description

This project turns a small LLM (Qwen/Qwen3-0.6B) into a function-calling
engine using **constrained decoding built from scratch**, without relying
on any structured-output library. Given a natural-language request and a
list of available functions, the program selects the correct function and
generates valid values for its parameters (numbers, integers, strings,
booleans, regex patterns), guaranteed to respect the required JSON schema.

## Algorithm Explanation

At each generation step, the model's raw logits (one score per vocabulary
token) are masked: only tokens that keep the output on track toward a
valid result are kept, everything else is set to `-inf`, then the
highest-scoring allowed token is picked (greedy decoding). Several
"allowed set" strategies are used depending on the parameter type:
- **Function names / booleans**: match against a fixed set of exact
  target strings (`compute_allowed`), narrowing as more characters match.
- **Numbers / integers**: no fixed target exists, so each candidate
  character is checked against digit/sign/decimal-point placement rules
  (`is_allowed_number_char`); integers additionally exclude the decimal
  point from the candidate set entirely. Generation stops at a JSON
  separator (`,`/`}`) or a length cap, and the final ids are decoded via
  the model's own `decode()` for consistency.
- **Strings**: open content, bounded by a closing quote acting as the
  stop signal.
- **Regex**: open content by default (`generate_regex_value`), with the
  first token forced to start a character class or escape sequence
  (`[` or `\`), a per-token repeat cap to break degenerate repetition
  loops, and backslash-collapsing post-processing. For parameter values
  matching a known, universally-standard linguistic category explicitly
  named in the request (digits, vowels, consonants, case, punctuation,
  whitespace, letters), the pattern is instead generated via the same
  target-matching mechanism as function names -- these are treated as a
  standard lookup, not creative generation. A specific quoted word
  (`\bword\b`) is left to open generation, since it already generates
  reliably without forcing.

## Design Decisions

- **Greedy `max()` over a small candidate set**, not full-vocabulary
  masking with `numpy`: since our allowed sets are already narrow
  (tens of tokens, not the full ~150k vocabulary), plain Python is
  measurably faster here.
- **Structural JSON is built in Python**, not generated by the model:
  the model only fills in values; punctuation (`{`, `,`, `}`) is
  written directly.
- **Extraction vs. generation, treated differently**: values that are
  literally present in the request (numbers, source strings, specific
  words) are treated as extraction and only lightly cued; values that
  require genuine synthesis (an arbitrary regex pattern) are left to
  open constrained generation, except for a small set of standard
  linguistic categories (vowels, digits, etc.) that have one universal
  regex representation and are treated as a lookup rather than
  creative generation.
- **Prompt engineering as a support layer, not a replacement**: cues
  built from the literal request sharpen the model's context, but the
  model still generates every open-ended value itself through
  constrained decoding.

## Performance Analysis

On the provided 11 test prompts, both function selection and argument
extraction are correct 11/11 (100%), comfortably meeting the required
90%+ threshold. Regex generation for standard linguistic categories is
guaranteed correct by construction; open-ended regex generation (for
patterns outside these categories) remains the main residual source of
error for prompts not covered by the current keyword set, given the
0.6B model's limited ability to synthesize correct regex syntax
unaided.

## Challenges Faced

- The tokenizer's byte-level BPE encoding hides spaces/newlines behind
  special characters (`Ġ`, `Ċ`); raw token concatenation produced
  garbled text until `model.decode()` was used on the generated ids.
- Number and string generation have no natural stopping point (the
  allowed set never becomes empty on its own), causing runaway
  generation until a length cap and JSON-separator stop tokens were
  added.
- Greedy decoding can fall into repetition loops; a per-value
  token-frequency cap was added to bound this.
- The model has a strong pretrained bias toward writing JSON-escaped
  double backslashes (`\\b`) even when generating raw, non-JSON-encoded
  text; a post-processing normalization step collapses repeated
  backslashes.
- Deciding how much prompt-level assistance is appropriate required
  drawing an explicit line between literal extraction (safe to cue
  strongly) and genuine content generation (left to the model, with
  only light contextual hints) so the model still does the actual
  constrained-decoding work the assignment requires.

## Testing Strategy

Each constrained-decoding function (`compute_allowed`,
`is_allowed_number_char`, `generate_regex_value`, etc.) was first
validated against small, hand-built vocabularies and fake logits to
confirm the masking/stopping logic in isolation, before running the
full pipeline against the real model. Edge cases (repeated substrings,
degenerate loops, malformed input files) were tested deliberately, not
just the happy path.

