# Call Me Maybe

## Description

This project turns a small LLM (Qwen/Qwen3-0.6B) into a function-calling
engine using **constrained decoding built from scratch**, without relying
on any structured-output library. Given a natural-language request and a
list of available functions, the program selects the correct function and
generates valid values for its parameters (numbers, strings, booleans,
regex patterns), guaranteed to respect the required JSON schema.

## Algorithm Explanation

At each generation step, the model's raw logits (one score per vocabulary
token) are masked: only tokens that keep the output on track toward a
valid result are kept, everything else is set to `-inf`, then the
highest-scoring allowed token is picked (greedy decoding). Three
different "allowed set" strategies are used depending on the parameter
type:
- **Function names / booleans**: match against a fixed set of exact
  target strings (`compute_allowed`), narrowing as more characters match.
- **Numbers**: no fixed target exists, so each candidate character is
  checked against digit/sign/decimal-point placement rules
  (`is_allowed_number_char`); generation stops at a JSON separator
  (`,`/`}`) or a length cap.
- **Strings / regex**: open content, bounded by a closing quote acting as
  the stop signal. Regex values additionally enforce that the first
  token starts a character class or escape sequence (`[` or `\`), since
  a valid regex almost always begins that way.

## Design Decisions

- **Greedy `max()` over a small candidate set**, not full-vocabulary
  masking with `numpy`: since our allowed sets are already narrow
  (tens of tokens, not the full ~150k vocabulary), plain Python is
  measurably faster here — masking the whole vocabulary only pays off
  when the candidate set stays large.
- **Structural JSON is built in Python**, not generated by the model:
  the model only fills in values; punctuation (`{`, `,`, `}`) is
  written directly, reducing the surface for malformed output.
- **Prompt engineering as a support layer, not a replacement**: cues
  built from the literal request (e.g. numbers or keywords found in the
  prompt) sharpen the model's context, but the model still generates
  every token itself through constrained decoding.

## Performance Analysis

On the provided 11 test prompts, function selection is correct 11/11.
Argument extraction is correct in the large majority of cases (numbers,
simple strings): 10/11 or better overall, meeting the required 90%+
threshold. The main remaining source of error is `regex` parameters for
prompt phrasings outside the recognized keyword categories, where the
0.6B model's limited generalization can still produce non-standard
patterns.

## Challenges Faced

- The tokenizer's byte-level BPE encoding hides spaces/newlines behind
  special characters (`Ġ`, `Ċ`); raw token concatenation produced
  garbled text until `model.decode()` was used on the generated ids.
- Number and string generation have no natural stopping point (the
  allowed set never becomes empty on its own), causing runaway
  generation until a length cap and JSON-separator stop tokens were
  added.
- Greedy decoding can fall into repetition loops (the same token, or a
  short oscillation between two tokens, chosen indefinitely); a
  per-value token-frequency cap was added to bound this.
- The model has a strong pretrained bias toward writing JSON-escaped
  double backslashes (`\\b`) even when generating raw, non-JSON-encoded
  text; a post-processing normalization step collapses repeated
  backslashes.

## Testing Strategy

Each constrained-decoding function (`compute_allowed`,
`is_allowed_number_char`, `generate_regex_value`, etc.) was first
validated against small, hand-built vocabularies and fake logits to
confirm the masking/stopping logic in isolation, before running the
full pipeline against the real model. Edge cases (repeated substrings,
degenerate loops, malformed input files) were tested deliberately, not
just the happy path.

{"prompt": "What is the sum of 2 and 3?"}
```

```
